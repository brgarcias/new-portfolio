# AGENTS.md

Instruções para agentes de código que trabalham neste repositório. O projeto é o portfólio profissional de Bruno Garcia, desenvolvedor full-stack. É um site de página única, em inglês, português e espanhol, feito com Next.js 16 (App Router), React 19, TypeScript estrito, Tailwind CSS 3, HeroUI e framer-motion, publicado no Netlify.

## Regra principal

O Bruno gosta do portfólio como ele é. Não mude a aparência nem o comportamento do site sem pedido explícito: cores, fontes, tamanhos, espaçamentos, animações, textos, ordem das seções e interações ficam como estão. Correções, atualizações de dependências e melhorias de desempenho e segurança precisam manter o resultado visual idêntico.

Os testes visuais de `tests/visual.spec.ts` garantem isso. Nunca regrave as imagens de `tests/snapshots/` para fazer um teste passar, a não ser que o pedido tenha sido justamente uma mudança visual. Nesse caso, confira cada imagem nova antes de versioná-la e diga no PR o que mudou.

Em outubro de 2026 o Bruno pediu um redesign, mais moderno e animado, que evoluiu a identidade do site: tema escuro, roxo `#5c5edc`, o nome espaçado e a ilustração. Ele foi feito em quatro etapas (PRs #19 a #22), cada uma aprovada por ele numa prévia. O visual que saiu daí é o que vale proteger agora. Depois veio um tema claro, com um botão na barra para trocar de tema. O tema escuro continua sendo o visual original. Quando o pedido for uma mudança visual, abra o PR com o link do Deploy Preview e só faça o merge depois que o Bruno aprovar a prévia no computador e no celular.

## Ambiente

- Use Node.js 24.22.1, a versão do `.nvmrc`. Rode `nvm use` antes de qualquer comando e confira com `node --version`, porque o shell pode abrir em outra versão. Se cada comando abrir um shell novo, ative o Node no mesmo comando, como em `nvm use >/dev/null && pnpm check`. O `.npmrc` tem `engine-strict=true`, então outra versão do Node faz a instalação falhar.
- Use somente pnpm 11.3.0, via Corepack. Não use npm nem yarn para instalar dependências e não crie outros lockfiles. O único lockfile é o `pnpm-lock.yaml`.
- Instale com `pnpm install --frozen-lockfile`.
- O `pnpm-workspace.yaml` libera scripts de instalação apenas para `@heroui/shared-utils`, que copia a variante para React 19 na instalação, e para `unrs-resolver`. Ele também aceita ESLint 10 nos plugins que ainda declaram suporte só até a versão 9. Mantenha essas regras ao mexer em dependências.

## Comandos

| Comando           | O que faz                                                         |
| ----------------- | ----------------------------------------------------------------- |
| `pnpm dev`        | Servidor de desenvolvimento em <http://localhost:3000>.           |
| `pnpm check`      | ESLint sem avisos, verificação de tipos e checagem do Prettier.   |
| `pnpm format:fix` | Aplica a formatação do Prettier.                                  |
| `pnpm build`      | Build de produção.                                                |
| `pnpm build:test` | Build de produção com a cópia fixa do conteúdo, para os testes.   |
| `pnpm test:e2e`   | Testes Playwright em desktop e celular sobre o build de produção. |

`pnpm typecheck` gera antes os tipos das rotas (`next typegen`), como `LayoutProps` e `PageProps`, que o CI ainda não tem quando roda o `pnpm check`. Os tipos que o `pnpm dev` gera em `.next/dev` não passam no TypeScript estrito do projeto; se o `pnpm build` reclamar de arquivos de lá, apague `.next/dev`.

`pnpm test:e2e` sobe o servidor com `pnpm start` na porta 4173, então rode `pnpm build:test` antes. Os testes usam uma cópia fixa do conteúdo, em `tests/fixtures/content`, para que as edições feitas no painel não mudem as capturas nem os textos que eles procuram; um build comum, com o conteúdo de `content/`, reprovaria os testes assim que o Bruno mudasse um texto. Para instalar o navegador, use `pnpm exec playwright install chromium`. Para usar um Chromium já instalado, defina `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`.

Antes de considerar uma mudança pronta, rode `pnpm check`, `pnpm build`, `pnpm build:test` e `pnpm test:e2e`, e confirme que tudo passa. No GitHub Actions, em `.github/workflows/ci.yml`, dois jobs `e2e` dividem os testes de navegador (`--shard`), cada um com o próprio build, e o primeiro também roda o `pnpm check`. O job `quality` espera os dois e falha se algum falhar: é ele o check que a `main` exige, em cada PR para `main`. Dividir em duas máquinas reduziu o tempo; mais workers na mesma máquina, não, porque a CPU dela já fica cheia com dois, e o teste mais longo passava do limite de tempo; o build com o conteúdo de verdade é o do Deploy Preview do Netlify, que também é um check obrigatório.

`pnpm dev` e `pnpm build` usam o webpack de propósito. O Turbopack minifica o CSS com o Lightning CSS, que reescreve `translate3d(...)`, `scale3d(...)` e `rotate3d(...)` como transformações 2D. A geometria é a mesma, mas o navegador deixa de criar camadas próprias para esses elementos e passa a desenhar imagens reduzidas com outra filtragem. Não troque para o Turbopack sem comparar as imagens dos testes visuais.

## Estrutura

- As páginas ficam em `src/app/[lang]/`, uma por idioma (`generateStaticParams`, com `dynamicParams = false`): a home, em `(site)/page.tsx`, e o jogo, em `play/page.tsx`. O inglês, idioma padrão, mora em `/` sem prefixo: o `next.config.mjs` reescreve `/` e `/play` para as páginas `/en` e `/en/play`, e redireciona quem abre `/en` ou `/en/play` para `/` e `/play`. Qualquer outro endereço não tem página e cai no `src/app/not-found.tsx`.
- `src/app/layout.tsx` só repassa a página, com os metadados que não dependem do idioma (ícones de `public/favicon/`, manifesto, verificação do Search Console) e as `<meta name="theme-color">`. Ele existe para o `not-found.tsx` poder renderizar o layout de `[lang]`: uma 404 lançada dentro de `[lang]`, com `notFound()`, não acha boundary acima do layout raiz e cai na página de erro do próprio Next.js, sem o HTML do site.
- `src/app/[lang]/layout.tsx` define o `lang` do `<html>` pelo idioma, a classe `dark`, as fontes Inter e Space Grotesk (esta para títulos, exposta como `--font-display`), o título, a descrição e as tags de compartilhamento no idioma, os `Providers` e o `I18nProvider`. A barra e o menu (`SiteFrame`) ficam no layout do grupo `(site)`, `src/app/[lang]/(site)/layout.tsx`, que envolve a home e a página de erro dela; o jogo, em `play/`, fica fora dele, sem barra, com a própria `error.tsx`. A 404 renderiza os dois layouts, e `src/components/StatusPage/ErrorPage.tsx` é a página de erro que os três `error.tsx` usam. O primeiro script do `<head>` remove a quebra de linha que o Netlify injeta, junto com um comentário, logo depois do `<meta charset>` nas páginas de produção em `*.netlify.app`. Sem ele, o React 19 falha na hidratação (erro #418) e renderiza a página inteira de novo. Não remova esse script; um teste simula a injeção. O segundo script aplica o tema antes do primeiro desenho da página, para ela nunca aparecer no outro tema.
- `src/app/theme.ts` cuida do tema. A classe `dark` ou `light` no `<html>` escolhe as cores do site e também as do HeroUI. Sem uma escolha do visitante, o site segue o tema do sistema e acompanha a troca dele na hora. A escolha fica no `localStorage`, na chave `theme`, e escolher o mesmo tema do sistema apaga a escolha, para o site voltar a segui-lo. O servidor não sabe o tema, então o script do `<head>` troca a classe antes de o React começar, e o `<html>` tem `suppressHydrationWarning`. Pelo mesmo motivo, o botão de tema (`src/components/SiteFrame/ThemeToggle.tsx`) tem os dois ícones e os dois rótulos na página, e o CSS mostra os do tema atual. Na troca, o novo tema se espalha num círculo que sai do botão (View Transitions), com as transições de CSS desligadas pela classe `theme-switching`; com "reduzir movimento" ou sem suporte, a troca é imediata. Com o menu aberto, as cores mudam aos poucos (`theme-fading`), sem o círculo: a captura da View Transition não guarda a página recuada em 3D em todos os navegadores. Nos dois casos, a página, as folhas atrás dela e o menu mantêm as próprias transições, para o menu abrir ou fechar no meio da troca. As duas `<meta name="theme-color">` seguem o tema, para a barra do navegador no celular. A `global-error` mantém o tema que a página tinha.
- `src/app/providers.tsx` envolve o site no `HeroUIProvider`, no `LazyMotion` do framer-motion, que baixa os recursos de animação depois do carregamento, e no `MotionConfig` com `reducedMotion="user"`, que segue a preferência do sistema por reduzir movimento.
- `src/app/[lang]/page.tsx` monta, numa rolagem só, o topo (`#top`) e as seções `#about`, `#experience`, `#education`, `#courses`, `#projects`, `#contributing` e `#contact`, nessa ordem. Ele passa ao topo o cargo atual, que é a experiência sem data de fim.
- `src/components/SiteFrame/` é a moldura do site: a barra fixa e o menu em pilha de páginas. A barra tem a marca, os links das seções (a partir de 1280 px de largura, onde a barra tem a largura máxima e os nomes em espanhol ainda cabem com folga), o seletor de idioma (a partir de 640 px), o botão de tema, o botão do currículo e o botão do menu, e destaca a seção que cruza o meio da tela com um `IntersectionObserver`. O menu vem da ideia do template da Codrops que o site usava: ao abrir, a página fica presa onde estava (`stage--locked`), recua em 3D (`stage--open`) e mostra duas folhas atrás dela; ao escolher uma seção, a página volta para a frente e rola até ela. O estado segue `closed`, `locked`, `open` e `closing`, e o fechamento termina no `transitionend` da página, ou na hora com "reduzir movimento". Um `clip-path` corta o que fica acima da rolagem, para a página recuada não cobrir o menu. Com o menu aberto (`site-header--menu-open`), os links, o seletor de idioma e o botão do currículo somem aos poucos, com desfoque, e o botão de tema desliza para junto do botão do menu, no lugar do currículo, com a mola `--ease-spring`; a distância (`--theme-shift`) é medida ao abrir. Eles voltam assim que o menu começa a fechar, e o X do botão do menu vira as três linhas ao mesmo tempo, mas os links só aceitam cliques com a página de volta. Com "reduzir movimento", tudo muda na hora. Fora da home, os links levam à home do idioma, como `/#<seção>`. O seletor de idioma (`LanguageSwitch.tsx`) abre, na barra, a lista dos idiomas pelo nome de cada um, e no menu mostra os três lado a lado; no celular, ele só aparece no menu. Os links carregam a página no outro idioma na seção que está na tela, como `/pt#projects`. O layout passa à moldura as seções do menu e as redes sociais, lidas do conteúdo; `content.ts` tem o currículo e o ícone de cada rede.
- Camadas: a página recuada fica em `z-index` 10, a área que a traz de volta em 20, o menu em 30 e a barra em 40. Os modais do HeroUI (50), inclusive os detalhes dos cursos, dos projetos e das fotos, cobrem a barra. Qualquer camada nova que precise cobrir a barra precisa de `z-index` acima de 40.
- `src/components/Section/` é o cabeçalho comum das seções: rótulo numerado, título e descrição e citação opcionais, que vêm de `content/site/sections.json`, o mesmo arquivo que o menu lê. A `<section>` tem `aria-labelledby` e `tabIndex={-1}`, para receber o foco quando o menu leva até ela.
- `src/components/Reveal/` faz a entrada dos blocos na primeira vez que aparecem na tela, com o `whileInView` do framer-motion: o bloco sobe numa mola e aparece num fade que termina junto com a subida, então um bloco com opacidade 1 já parou, como os testes esperam. A mola é a função `spring`, de `src/components/spring.ts`, a mesma curva de `--ease-spring`, numa animação de duração fixa; o diálogo usa a mesma.
- `src/components/Tactile/`, montado nos `Providers`, faz os botões, os links que funcionam como botões e os cartões cobertos por um botão encolherem um pouco sob o dedo e voltarem numa mola, como no iPhone. Ele anima a propriedade `scale`, que se soma aos `transform` dos elementos, como a subida no hover. Um botão pequeno encolhe para 94%, e um elemento grande, como o título de uma experiência ou um cartão, quase não encolhe: as bordas andam no máximo 2 px. Com o mouse, o clique vale onde o botão é solto, e uma borda que andasse mais deixava o ponteiro fora do elemento, como na seta do título das experiências. A lista do que encolhe fica no próprio arquivo; ao criar um botão novo, acrescente a classe dele.
- `src/components/OffscreenPause/`, na página, pausa as animações em loop das partes marcadas com `data-loop` (o topo e a faixa de tecnologias) enquanto elas estão fora da tela, para a página trabalhar menos ao rolar.
- `src/app/about-me/` tem o topo, com o cargo atual, o nome, o título, os botões (entre eles o "Play", que leva ao jogo em `/play` no idioma da página), as redes sociais e a ilustração com tecnologias flutuando, e a seção About, com o texto e a lista de tecnologias. O texto é longo, então fica no tamanho do resto do site, com o primeiro parágrafo destacado só pela cor, e no computador a lista acompanha o texto na tela (`position: sticky`).
- `src/app/professional-experience/` é a linha do tempo. Cada cargo tem a empresa e o período, um nó no trilho e um cartão com o título, as tags de tecnologia e os detalhes, que abrem e fecham pelo título (`aria-expanded`). O trilho se desenha conforme a rolagem, até o meio da tela, e cada nó acende quando o desenho chega a ele. `TechRibbon` fecha a seção com todas as tecnologias das experiências, em duas faixas que deslizam em sentidos opostos; ela é decorativa (`aria-hidden`), porque as mesmas tecnologias aparecem nos cartões.
- `src/app/academic-education/` mostra as etapas da formação como abas (`tablist`), num trilho com um capelo que desliza até a etapa escolhida, como a caixa de presente do layout antigo. As setas, Home e End trocam de etapa. As etapas futuras (`upcoming`) têm borda e trilho tracejados.
- `src/app/courses/` mostra os cursos numa grade de cartões, em que os dois cursos com `wide` ocupam duas colunas. Cada cartão brilha com a cor do bloco que o curso tinha no layout antigo. O título do cartão é um botão que cobre o cartão inteiro e abre o diálogo com os módulos.
- `src/app/projects/` mostra os projetos num carrossel que atravessa a tela, com rolagem horizontal e `scroll-snap`, para deslizar no celular. Cada cartão tem o aparelho com a prévia do site, que se inclina na direção do mouse no computador. A prévia cobre a tela do aparelho, alinhada ao topo, e o que passa da altura é cortado embaixo. As setas dão a volta e, enquanto a faixa desliza até o cartão escolhido, contam a partir dele. O cartão atual (`aria-current`) é o que está no começo da faixa, seja qual for o jeito de chegar até ele. Os detalhes abrem no diálogo do HeroUI, com a imagem grande, o texto e o link do site.
- `src/app/contributing/` conta por que o Bruno participa de ações voluntárias, mostra as fotos das iniciativas e fecha com os números. Cada foto abre maior num diálogo, com a descrição, e as setas, na tela ou no teclado, passam pelas outras fotos.
- `src/app/contact/` mostra, em cartões, os dados que antes ficavam em abas: perfil, formação, contato (com links de e-mail e telefone) e idiomas, seguidos dos botões das redes sociais.
- `src/app/game/` é o jogo da página `/play`: um mundo 3D em que o visitante pilota uma nave do Star Wars, escolhida num hangar, por uma plataforma no espaço com uma plataforma de pouso para cada seção do site. `index.tsx` confere se o navegador desenha WebGL e só então baixa, com `next/dynamic`, o `Game.tsx` e o three.js; o site não carrega nada disso. `physics.ts` é o voo rasante (empuxo, inércia, giro, colisão com os obstáculos e com a borda da plataforma), em aritmética pura, sem motor de física; `controls.ts` junta o teclado e o joystick de toque num objeto de módulo que cada quadro lê; `ships/` tem as seis naves, montadas em código a partir de formas simples (`parts.ts`), com os nomes reais das naves do Star Wars, decisão do Bruno, que assume o risco de direitos; nunca baixe modelos de terceiros. `world/arena.ts` tem a plataforma, as plataformas de pouso, os obstáculos e as plantas, gerados por uma sequência aleatória fixa, com a rota do começo até a primeira plataforma sempre livre; `world/biomes.ts` divide a plataforma em sete setores, um por seção, cada um vestido de um planeta da saga (Tatooine, Coruscant, Dagobah, Kamino, Naboo, Endor e Hoth, nomes que o Bruno assume como assumiu os das naves), com as cores do chão, a paleta do céu, da névoa e das luzes, o clima e a cor de destaque, e `sectorAt` diz em que setor um ponto está (o centro é o hub, um convés no espaço); `world/World.tsx` compõe tudo: `Ground.tsx` é o chão, um disco só cujos vértices levam a cor e o relevo do setor (dunas, neve), plano sob as plataformas, com a borda acesa na cor de cada setor; `builder.ts` junta formas simples, cada uma numa cor chapada, numa geometria só por setor, com as cores nos vértices (e as partes acesas, como janelas, numa segunda, sem luz), para cada setor sair em uma ou duas chamadas de desenho; `props.ts` veste cada obstáculo conforme o setor (vaporizadores e um sandcrawler, torres com andares acesos, árvores retorcidas e a cabana do mestre, salões sobre estacas no mar, casas de domo verde, sequoias com cabanas, espirais de gelo e a entrada da base) e desenha as plantas (arbustos, cogumelos que brilham, árvores, flores, samambaias, cristais, e um X-wing afundado no pântano, cozido na mesma geometria); `Fauna.tsx` são os bichos de cada setor (banthas, speeders nas vias da cidade, sapos, aiwhas voando em círculos, shaaks, ewoks e tauntauns), um `InstancedMesh` por espécie, que o quadro move dentro do próprio setor, longe das plataformas e dos obstáculos, e que param com "reduzir movimento"; `Weather.tsx` é o clima de cada setor (areia, esporos, chuva, pólen, vagalumes e neve), pontos que o shader move com só o tempo como uniform; `Water.tsx` é a água (o mar de Kamino, o lago de Naboo, que escorre em duas cachoeiras pela borda, e as poças de Dagobah), com shaders simples; `Atmosphere.tsx` é o céu (um shader com as cores do alto, do horizonte e de baixo), as estrelas, a névoa e as luzes, que seguem o setor da nave (`atmosphere.sector`, que `Ship.tsx` escreve) numa transição suave, com relâmpagos sobre Kamino; `Far.tsx` são as vistas longe de cada planeta (os dois sóis, o gigante gasoso, a silhueta da cidade e as nuvens). As geometrias por quadro mudam só por objetos de módulo (os uniforms de tempo, as cores do céu, os rebanhos), porque o React Compiler não aceita mudar valores de `useMemo` nos callbacks. O HUD mostra o planeta sob a nave (`.hud__planet`, que o quadro troca pelo atributo `hidden`), o radar pinta os setores e os rótulos das plataformas trazem o planeta; `Adaptive.tsx` baixa a resolução do canvas, um quarto por vez, depois de meio segundo de quadros lentos, como num celular fraco ou no renderizador por software do CI, e a devolve depois de quatro segundos de quadros rápidos; `Ship.tsx` move a nave e a câmera a cada quadro, sacode a câmera numa batida, com a física em passos fixos de 1/60 s que somam o tempo do quadro (até 1 s), para um quadro lento, como no renderizador por software do CI ou num celular fraco, não deixar o jogo em câmera lenta; `Labels.tsx` mantém os nomes das seções, em HTML, sobre as plataformas; `Hud.tsx` tem a volta, a troca de nave, a contagem de seções abertas, o radar (`Radar.tsx`, um SVG com as plataformas, em que o quadro move a nave), a plataforma atual, o aviso quando todas as seções foram abertas e os controles; `Hangar.tsx` é a escolha da nave, guardada no `localStorage` (`ship`). Os elementos que o quadro escreve (o HUD, com a posição, o rumo, a velocidade e o tempo de voo em atributos `data-*`, e os rótulos) se registram em `overlay.ts`. As regras do React Compiler no ESLint não aceitam mudar props nem valores de hooks nos callbacks, por isso o estado do voo, os controles e esses elementos são objetos de módulo. Uma plataforma de pouso segura a nave (`physics.ts`), e quando ela para ali por meio segundo o jogo abre a seção daquela plataforma em `Panel.tsx`, um diálogo sobre o voo com o mesmo componente que a home usa, renderizado no servidor por `play/page.tsx` e passado ao jogo como `panels`; a seção About tem o próprio componente, `src/app/about-me/About.tsx`, para o jogo não trazer o topo junto. O painel fecha pelo botão, por Escape ou por um clique fora, e a plataforma só abre de novo quando a nave sai e volta. Os textos do jogo ficam em `game`, nas mensagens de `src/i18n/messages/`.
- `src/components/SiteFrame/SiteFooter.tsx` é o rodapé de todas as páginas, dentro da folha que recua com o menu: marca, redes sociais, o ano e, na home, o link de volta ao topo. O ano vem do layout, calculado no servidor, para a página e o navegador mostrarem o mesmo.
- `src/app/<seção>/` tem o componente da seção e o `styles.css` próprio. Os textos e os itens de cada seção ficam em `content/`, veja a seção Conteúdo.
- `src/content/` lê o conteúdo de `content/` para um idioma e entrega às seções o que elas mostram: `src/app/[lang]/page.tsx` carrega tudo no servidor e passa por props, e o layout carrega o perfil e as seções do menu. Só o servidor lê os arquivos; os componentes do navegador importam apenas os tipos e `src/content/sections.ts`, a ordem das seções. `src/components/Markup` formata os textos do conteúdo.
- `src/i18n/` cuida dos idiomas. `config.ts` lista os idiomas e dá o endereço da home de cada um. `messages/en.ts` tem os textos da interface (botões, rótulos, avisos, a 404 e a página de erro), separados do conteúdo; `{nome}` marca um valor preenchido na hora, com `format`. Os componentes do servidor recebem os textos por props; os do navegador leem com `useI18n()`, do `I18nProvider` que o layout de `[lang]` põe em volta da moldura. Sem esse provedor, como na `global-error`, os textos ficam em inglês.
- `src/components/Modal`, `Form` e `SnackBar` são o modal do HeroUI usado pelo feedback, pelos cursos e pelos projetos, o formulário de feedback e o aviso de envio, que tem `role="status"` para os leitores de tela e um botão de fechar. O título do modal é um `h2` no cabeçalho, e o HeroUI dá ao diálogo o nome do cabeçalho. O diálogo entra numa mola (`motionProps`): no celular sobe de baixo, e nas telas maiores cresce de 96%, com as variáveis `--slide-*` e `--scale-*` do HeroUI. Diálogos só com texto, como os dos cursos, usam `focusableBody`, para o teclado conseguir rolar o conteúdo. As seções usam o diálogo por `src/components/Modal/Lazy.tsx`, que só baixa o código do HeroUI quando o navegador fica ocioso depois da página, ou quando um diálogo abre antes disso; o formulário de feedback carrega do mesmo jeito. Os botões que abrem diálogos importam `openOnKey` de `src/components/Modal/openOnKey.ts`. Importar o `Modal` ou o `Form` diretamente numa seção traz de volta, ao primeiro carregamento, cerca de 50 KB de JavaScript.
- `src/app/globals.css` tem as diretivas do Tailwind, os tokens de design em `:root` (altura da barra, larguras, margens, o recuo do menu e as curvas de animação: o site se move em molas, como o iPhone, feitas com `linear()`. `--ease-spring` passa 2% do fim e volta, e `--ease-out`, usada na maior parte dos movimentos, é a mesma mola; `--ease-stack`, da página do menu e das superfícies grandes, chega ao fim sem passar dele. Navegadores sem `linear()` usam curvas sem mola), as cores do tema escuro em `:root, .dark` e as do tema claro em `.light`, a base, os botões (`.btn` com `--primary`, `--ghost`, `--text` e `--small`), as tags (`.tag-list` e `.tag`), o cabeçalho das seções e as páginas de status.
- `src/app/not-found.tsx` (404, que renderiza o layout de `[lang]` no idioma padrão e a página de `src/components/StatusPage/NotFound.tsx`), `src/app/[lang]/error.tsx` (erro na página) e `src/app/global-error.tsx` (erro no próprio layout, com `<html>` e `<body>` próprios) usam `src/components/StatusPage`: rótulo, código opcional (o "404" em gradiente), título, descrição, citação e botões de ação. A 404 e a página de erro aparecem com a barra e o menu; a `global-error` substitui o layout e fica sem eles. As regras dessas páginas ficam no `globals.css` porque um CSS importado pelo `not-found.tsx` seria pré-carregado, sem uso, em todas as páginas. O "Try again" recarrega a página inteira, porque o `reset()` do Next não ligaria a barra às seções novas. Os links da 404 também carregam a página de novo: a 404 renderiza o layout fora das rotas, e uma navegação dentro do app reconstruiria o `<html>`, perdendo a classe do tema.
- O primeiro elemento focável de toda página é o link "Skip to content", escondido até receber foco, que leva ao `<main id="main">`. A home, a 404 e as páginas de erro têm esse `main`; mantenha o `id` ao criar outras páginas.
- O `SiteFrame` usa `usePathname` para saber se está na home. No servidor, a home em inglês aparece como `/en`, para onde `/` é reescrito, e no navegador como `/`; os dois contam como home. Se o servidor e o navegador discordarem, os links e o rodapé mudam, a hidratação falha e o React refaz a página inteira, duplicando os scripts do `<head>` e perdendo o tema.
- `next.config.mjs` desliga o `agentRules`, esconde o `X-Powered-By` e define os cabeçalhos de segurança: Content Security Policy, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy` e `Permissions-Policy`. A CSP só aceita recursos do próprio site. Não carregue scripts, estilos, fontes ou imagens de outros domínios. Se isso for inevitável, ajuste a política e explique o motivo no PR. O jogo em `/play` vive com a política do site: não usa WebAssembly nem recurso de fora. O painel em `/admin` tem uma política própria, que só vale lá: ele fala com a API do GitHub e com o login do Netlify, mostra os avatares e as imagens do repositório, lê as imagens que envia por endereços `blob:` e precisa de `'unsafe-eval'`, porque a checagem da configuração do Decap (AJV) compila código, e de `'wasm-unsafe-eval'` para as ferramentas de imagem.
- `public/` guarda favicon, imagens, o currículo em `documents/cv/Bruno_Garcia_Resume.zip` e `contact.html`, que declara o formulário para o Netlify Forms.
- O painel de conteúdo (Decap CMS) fica em `/admin`. A página é a rota `src/app/admin/route.ts`, e não um arquivo em `public/`, porque o Netlify serve os arquivos de `public/` direto da CDN, sem os cabeçalhos de segurança do `next.config.mjs`. Ela carrega o Decap de `public/admin/cms/`, servido pelo próprio site, e `public/admin/config.yml` descreve as coleções, que espelham `content/`, com os rótulos e as dicas em português. O login é com o GitHub, pelo provedor de OAuth do Netlify (`site_domain` aponta para o site, para funcionar também nas prévias e no localhost); só quem pode escrever no repositório entra. Cada alteração vira um PR (`editorial_workflow`) com Deploy Preview, e "Publicar" faz o merge com squash depois que os checks passam. No localhost, com o `decap-server` rodando, o painel usa a cópia local, sem login (`local_backend`).
- `public/admin/panel.js` carrega antes do Decap, que espera por ele (`CMS_MANUAL_INIT`), adapta o backend do GitHub e só então inicia o painel. O Decap grava os commits pela Git Data API, que os deixa sem assinatura, e a `main` só aceita commits verificados, por PR. Por isso cada salvamento vira um único commit feito pela mutação `createCommitOnBranch` do GraphQL, que o GitHub assina, e um PR que ficou atrás da `main` recebe a `main` por um merge que o GitHub também assina, no lugar do rebase que o Decap fazia. O painel nunca grava direto na `main`: despublicar um item, enviar ou apagar arquivos na biblioteca de mídia e o commit direto que o Decap tenta quando o GitHub recusa um merge (`forceMergePR`) param com um aviso. As imagens de um item vão no PR dele.
- Um cartão no canto do painel (`public/admin/panel.css`) mostra os checks do PR do item aberto, ou todos os PRs abertos no fluxo de trabalho, com os links do PR e da prévia e o botão que atualiza o PR com a `main`. Ele lê o GitHub a cada 15 segundos enquanto há checks rodando. "Publicar" só faz o merge com todos os checks verdes e o merge liberado pelo GitHub (`mergeStateStatus` `CLEAN`): até lá, os botões de publicar ficam apagados e um clique neles abre o cartão, e o evento `prePublish` confere o GitHub de novo antes do merge, caso o cartão esteja desatualizado. Os botões são achados pelas classes do emotion do Decap 3.17.1 (`e1d2l9mo5`, `ewffzyy0` e `ewffzyy1`).
- `src/emails/feedback/index.html` é um modelo de e-mail do SendGrid mantido fora do build. O site não o usa e o Prettier o ignora.
- `tests/portfolio.spec.ts` tem os testes funcionais, `tests/visual.spec.ts` os testes visuais, `tests/panel.spec.ts` os testes do painel, que respondem pelo GitHub, `tests/game.spec.ts` os testes do jogo, `tests/helpers.ts` a navegação compartilhada e `tests/snapshots/` as imagens de referência.

O projeto usa o App Router. As seções são componentes de servidor quando não precisam de estado; os interativos têm `'use client'`.

## Conteúdo

- O site tem três idiomas: inglês, o padrão, em `/`, português em `/pt` e espanhol em `/es`. Todo texto visível existe nos três: o conteúdo nos blocos `en`, `pt` e `es` dos arquivos de `content/`, e os textos da interface em `src/i18n/messages/`, em que `pt.ts` e `es.ts` seguem o formato de `en.ts` (o TypeScript confere). Ao mudar um texto, mude os três. As traduções são fiéis ao inglês, sem acrescentar nada, mantêm os nomes próprios (escolas, empresas, tecnologias e nomes de cursos) e passam pela revisão do Bruno. Os rótulos curtos da barra precisam caber nela: em espanhol, "Contribuir" no lugar de "Contribuciones".
- Cada idioma tem a URL canônica própria e aponta para os outros com `hreflang` (e `x-default` para o inglês), e o `sitemap.xml` lista os três. A 404 fica em inglês em qualquer endereço.
- Documentação, títulos e descrições de PRs e títulos de testes ficam em português.
- Nunca invente experiências, projetos, cursos, métricas, depoimentos ou datas. Se faltar uma informação, pergunte.
- O conteúdo das seções fica em `content/`, em JSON, do jeito que o painel de conteúdo (Decap CMS) salva com a estrutura `single_file`: cada arquivo tem um bloco por idioma (`en`, `pt`, `es`), e o que uma tradução deixa vazio vem do inglês, campo por campo. Os arquivos únicos ficam em `content/site/` (perfil, topo, About, cabeçalhos das seções, Contribuições e cartões de contato). As listas têm um arquivo por item: `content/experiences/`, `education/`, `courses/`, `projects/` e `initiatives/` (as fotos de Contribuições). Os itens com o campo `order` aparecem nessa ordem; as experiências, pela data de início.
- O Prettier ignora `content/`, porque o painel grava o JSON no formato dele, sem passar pelo hook de pre-commit, e o `prettier --check` reprovaria os PRs do painel. Ao editar à mão, mantenha o formato de `JSON.stringify(dados, null, 2)`.
- O Bruno edita o conteúdo pelo painel, em `/admin`. Ao mudar a estrutura do conteúdo (um campo novo, renomeado ou removido), atualize juntos os tipos de `src/content/types.ts`, os arquivos de `content/`, a cópia dos testes em `tests/fixtures/content/` e os campos de `public/admin/config.yml`, com `i18n: true` nos campos traduzidos e `i18n: duplicate` nos que são iguais nos três idiomas (no Decap, listas só aceitam `i18n: true`).
- Textos do conteúdo aceitam `**destaque**`, que leva o gradiente da marca (ou, no título do topo, o gradiente do título), `*ênfase*` e `[texto](endereço)`. Links para `whatsapp` ou `email` levam aos canais do perfil, e links para outros sites abrem em outra aba. Campos de texto longo separam parágrafos com uma linha em branco, e listas de tecnologias separam os nomes por vírgula.
- Imagens do conteúdo, como as prévias dos projetos e as fotos de Contribuições, são caminhos em `public/`, como `/images/projects/malka.webp`, e `src/content/image.ts` lê o tamanho delas no próprio arquivo, para o `next/image`. Os aparelhos dos projetos são escolhidos pelo nome (`iphone`, `ipad`, `macbook`, `imac` e `watch`) e ficam no código, com a posição da tela em cada imagem, medida nos pixels da imagem (`devices`, em `src/app/projects/index.tsx`). Ao trocar a imagem de um aparelho, meça a tela de novo. A página é gerada de novo no servidor uma vez por dia, então o `next.config.mjs` inclui `content/` e `public/images/` no pacote do servidor (`outputFileTracingIncludes`). Os caminhos lidos pelo servidor partem de pastas escritas no código (`content`, `tests/fixtures/content`, `public/images`): de um caminho que o build não consegue ler, como um vindo de variável de ambiente, o Next.js copia o projeto inteiro, `.git` incluído, para a função do servidor, e o Netlify recusa o deploy por tamanho (`request body too large`).
- As experiências ficam em `content/experiences/`, um arquivo por cargo. As datas (`start` e `end`) usam o formato `AAAA-MM`, e o período e a duração são calculados a partir delas. A experiência sem data de fim é a atual. Os detalhes são grupos de itens, cada um com um título opcional.
- As tags de cada experiência (`stack`) só repetem tecnologias que a descrição dela cita, com o nome oficial (Node.js, Next.js, React). A faixa de tecnologias junta as tags de todas, da experiência mais recente para a mais antiga. Ao mudar uma descrição, confira as tags.
- Datas no formato `AAAA-MM` ou `AAAA-MM-DD` são lidas como meia-noite UTC, então todo cálculo e toda formatação de data usam UTC (`getUTCMonth`, `timeZone: 'UTC'`). Com o fuso local, um build feito no Brasil mostraria o mês anterior. Um teste confere os períodos.
- A duração do emprego atual e a idade na seção de contato dependem da data de hoje. Elas são calculadas a cada renderização, por `getExperiences()` e `getContactCards()`, de `src/content/`, e a página inicial é regenerada uma vez por dia (`revalidate = 86400` em `src/app/page.tsx`). Não volte a calcular esses valores no nível do módulo, porque o servidor guarda o módulo carregado e os valores ficariam congelados.
- O cargo atual que aparece no topo vem da experiência sem data de fim, sem o trecho entre parênteses do título. As tecnologias do topo (`content/site/hero.json`) e da seção About (`content/site/about.json`) repetem as que o texto da seção cita.
- Nome, cargo, data de nascimento, e-mail, telefone, a mensagem do WhatsApp, LinkedIn e GitHub ficam só em `content/site/profile.json`, que alimenta o topo, o menu, o rodapé, os cartões e os botões de contato, o link "text me" e os dados estruturados. O link do WhatsApp e o do telefone usam os dígitos do telefone. Ao trocar um contato, atualize os testes.
- O currículo é `public/documents/cv/Bruno_Garcia_Resume.zip`, baixado por um link com `download`. Os testes conferem o nome do download e que o arquivo é um ZIP.
- O formulário de feedback envia os dados ao Netlify Forms, no formulário `contact`, com um `POST` para `public/contact.html`, o arquivo estático que o Netlify lê no deploy. Um `POST` para `/` chega ao servidor do Next.js, responde 200 e a mensagem se perde. O Netlify só aceita campos declarados em `contact.html`, então qualquer campo novo ou renomeado em `src/components/Form` precisa ser atualizado lá também; um teste confere isso. O campo `bot-field` é uma armadilha para robôs e fica vazio. Não adicione outros formulários, servidores de envio nem simulações de envio.
- O endereço oficial é <https://brgarcias-portfolio.netlify.app>, definido em `siteUrl`, em `src/app/site.ts`. Ele alimenta a URL canônica, o Open Graph, os dados estruturados `Person` de `src/app/layout.tsx`, o `robots.txt` (`src/app/robots.ts`) e o `sitemap.xml` (`src/app/sitemap.ts`), e também aparece em `package.json`. Ao trocar o domínio, atualize esses lugares e a propriedade do Search Console.
- Os dados estruturados `Person` só repetem fatos que a página já mostra: nome, cargo, e-mail, LinkedIn e GitHub. Mantenha-os em sincronia com o conteúdo.
- O site é verificado no Google Search Console como propriedade de prefixo do URL, pela meta tag `google-site-verification`, com o token em `verification.google` de `src/app/layout.tsx`. Não remova a tag. Uma propriedade do tipo Domínio só verifica por DNS e não funciona em `netlify.app`.

## Código

- TypeScript estrito, com `noUnusedLocals` e `noUnusedParameters`. O alias `@/` aponta para a raiz do repositório, então os imports são `@/src/...` e `@/public/...`.
- Siga o estilo do arquivo ao redor: componentes com exportação padrão, comentários de grupo nos imports (`// HOOKS`, `// FONTAWESOME`), nomes e classes em inglês.
- Prettier com aspas simples e vírgula final. Indentação de dois espaços e quebras de linha LF.
- Os estilos ficam no `styles.css` de cada seção ou componente e no `globals.css`. Use os tokens de `:root`, como `--color-brand`, `--gradient-brand`, `--header-height`, `--container`, `--gutter` e `--ease-out`, em vez de valores soltos.
- Toda cor existe nos dois temas. Use os tokens de cor, que mudam com o tema, como `--color-text`, `--color-surface`, `--color-border` e `--color-fill`. Para cores translúcidas, use os canais, como em `rgb(var(--rgb-veil) / 0.06)`: o véu é branco no tema escuro e tinta no claro. Uma cor nova entra em `:root, .dark` e em `.light`, com o valor do tema escuro igual ao que a regra tinha, para o tema escuro não mudar nem um pixel. O que só muda no tema claro, como sombras e brilhos mais suaves, fica no fim do `styles.css` do componente, em regras `.light ...`. O que fica sobre fotos, como a legenda das contribuições, usa cores fixas, iguais nos dois temas. Textos pequenos precisam de contraste de pelo menos 4,5:1 nos dois temas. Não converta CSS para Tailwind e, sem um pedido de mudança visual, não reorganize as folhas de estilo nem troque valores por equivalentes "mais limpos": até mudanças de mesma geometria podem alterar a renderização. O Tailwind serve ao HeroUI e a poucas classes utilitárias. O `content` do `tailwind.config.ts` lê só os componentes do HeroUI que o site usa (botão, campo, modal, espaçador e spinner); ao usar outro, acrescente-o à lista, ou ele fica sem estilo.
- Animações que se repetem, como os brilhos, a flutuação, o gradiente do título e a faixa de tecnologias, são CSS, que o Playwright congela nas capturas. Elas ficam em partes marcadas com `data-loop`, que pausam fora da tela.
- Movimentos usam as molas de `:root` (`--ease-out` ou `--ease-spring`, e `--ease-stack` para superfícies grandes), e não curvas soltas. A mola passa um pouco do fim: não a use onde isso apareça fora do lugar, como no preenchimento do trilho da formação, que usa `--ease-stack`.
- Animações ligadas à rolagem, como o trilho das experiências, usam `animation-timeline` do CSS dentro de `@supports (animation-timeline: view())` e de `prefers-reduced-motion: no-preference`. O estilo fora da animação é o estado final, então navegadores sem suporte, quem pede menos movimento e as capturas do Playwright veem o desenho completo. Use `view-timeline-inset: 0px` (ou `view(block 0px)`): sem isso, a linha do tempo desconta o `scroll-padding-top` da barra e o desenho escorrega para baixo do meio da tela.
- O que só aparece durante uma animação contínua, como o anel que pulsa no cargo atual, fica invisível fora dela. O Playwright para as animações nas capturas, e um elemento parado por cima de outro mudava um nível de cor na borda a cada execução. O framer-motion serve só às entradas que acontecem uma vez, com componentes `m.` dentro do `LazyMotion`; não use `motion.`, que traria o pacote inteiro no primeiro carregamento. A entrada do topo é CSS, para o texto aparecer no primeiro desenho da página, sem esperar o JavaScript. Toda animação respeita `prefers-reduced-motion`: as de CSS por media query e as do framer-motion pelo `MotionConfig`.
- Ícones vêm do FontAwesome 6, com `@fortawesome/react-fontawesome`.
- Imagens são exibidas com `next/image`, com `unoptimized`, e ficam em WebP dentro de `public/images/`. As do código, como a ilustração do topo e os aparelhos dos projetos, são importadas estaticamente; as do conteúdo são caminhos, com o tamanho lido do arquivo. Capturas de tela, mockups e ilustrações usam WebP sem perdas, que mantém cada pixel do PNG original. Fotos usam WebP com qualidade 82 e lado menor de 1200 px, o bastante para os cartões em telas de alta densidade, mantendo o perfil de cor (as fotos de celular vêm em Display P3).
- Remova metadados, como localização, de qualquer foto antes de publicá-la. As fotos de contribuição tinham coordenadas GPS no EXIF. Uma forma de converter uma foto com o `sharp` é `sharp(origem).resize({ width: 1200 }).keepIccProfile().webp({ quality: 82, effort: 6 }).toFile(destino)`, que descarta o EXIF. Use `height` no lugar de `width` para fotos na horizontal.
- As imagens carregam conforme a rolagem se aproxima delas, o padrão do `next/image`; só a ilustração do topo carrega antes (`priority`). Os diálogos só existem enquanto estão abertos, então a imagem grande de cada projeto só baixa quando o visitante abre os detalhes. Mantenha as imagens leves: uma imagem mostrada pequena ganha uma cópia com o dobro do tamanho em que aparece, como as miniaturas `*-thumb.webp` das contribuições, cujos originais só abrem no visualizador, e as prévias dos sites nos aparelhos dos projetos.
- O projeto tem poucas dependências de produção. Evite adicionar novas e justifique no PR quando for necessário.
- Fontes são servidas pelo próprio projeto, pelo `next/font` ou por arquivos em `public/fonts/`. Não use CDNs de fontes, estilos ou scripts, que a CSP bloqueia.
- Não edite `next-env.d.ts`, que é gerado pelo Next.js. Não versione `.next/`, `test-results/`, `playwright-report/` nem `tsconfig.tsbuildinfo`.

### Versões que não devem subir sem cuidado

- **Tailwind CSS** fica na 3.4. A versão 4 muda o reset de estilos e o HeroUI 2.8 em diante exige a 4.
- **HeroUI** fica em `@heroui/react` 2.7.11, a última linha compatível com Tailwind 3. O `Modal` fixa `max-h-[calc(100%_-_7.5rem)]`, porque o HeroUI mudou esse limite para 8rem.
- **FontAwesome** fica na 6.x. A versão 7 redesenhou ícones e mudou a largura padrão.
- **Playwright**: a versão de `@playwright/test` precisa ser igual à tag do contêiner em `.github/workflows/ci.yml`. Ao atualizar, regrave as imagens dos testes visuais e confira que nada mudou além do esperado.
- **three** e **@react-three/fiber** ficam na 0.186 e na 9.x: a linha 9 do fiber é a feita para o React 19. Atualize os dois juntos e abra `/play` para conferir as naves e o voo.
- **Decap CMS** fica na 3.17.1, copiada do pacote `decap-cms` do npm para `public/admin/cms/` (o `decap-cms.js`, os pedaços `*.decap-cms.js`, os dois `.wasm` e a licença). Para atualizar, baixe o `.tgz` da versão nova do registro do npm, confira o `integrity` que o registro informa, troque esses arquivos, atualize a versão aqui, e abra o painel para conferir que ele carrega sem violações da CSP. Confira também o que `public/admin/panel.js` usa do Decap: o registro do backend `github` (`CMS.getBackend`), o `authenticate` e o `logout` dele, os métodos da API que ele troca (`persistFiles`, `deleteFiles` e `forceMergePR`) e os que ele chama, e as classes dos botões de publicar. Os testes de `tests/panel.spec.ts` passam por esse caminho.

## Testes

Os testes de navegador são o contrato de qualidade do site. Eles exigem:

- Nenhum erro de JavaScript no carregamento e nenhuma rolagem horizontal.
- Menu em pilha que leva a todas as seções, fecha com Escape ou com um clique na página, aguenta cliques rápidos e respeita "reduzir movimento", e barra que destaca a seção na tela e, com o menu aberto, junta o botão de tema ao do menu.
- Experiências que abrem e recolhem, com tags e a faixa de tecnologias; etapas da formação que trocam pelo clique e pelo teclado; cursos que abrem pelo clique e pelo teclado, num diálogo com o nome do curso; projetos que trocam pelas setas, que dão a volta, e pela rolagem, com a prévia cobrindo a tela de cada aparelho e detalhes num diálogo; fotos das contribuições que abrem maiores e passam pelas setas e pelo teclado; cartões de contato com os links de e-mail e telefone; e o rodapé, com o ano e a volta ao topo.
- Download do currículo, links de contato corretos e o botão do topo que leva ao jogo no idioma da página.
- Validação, aviso de sucesso e aviso de erro do formulário de feedback, com o aviso anunciado aos leitores de tela e fechável pelo botão e por Escape.
- Página 404 com status 404, `noindex`, barra com links para as seções da home e link de volta, depois do qual o menu da home funciona.
- Páginas em português e em espanhol, com o `lang` certo, os textos e as datas no idioma e os `hreflang`; o seletor troca o idioma na barra e no menu e mantém a seção na tela; e `/en` leva para `/`.
- Páginas de erro que aparecem quando uma seção ou o layout falham (os testes tiram o `IntersectionObserver` do navegador ou fazem a barra falhar ao observar o topo), com "Try again" que recupera o site.
- Cabeçalhos de segurança presentes e nenhuma violação da Content Security Policy ao navegar, abrir os modais e enviar o feedback.
- Painel de conteúdo em `/admin`, com a política de segurança própria, fora dos buscadores, e o login do GitHub, que o Decap só mostra com a configuração válida.
- Painel ligado a um GitHub simulado, no computador: o cartão com os checks do PR e com os PRs abertos do fluxo de trabalho; "Publicar" apagado até tudo ficar verde, recusado quando o GitHub ainda não liberou o merge, mesmo com o cartão desatualizado, e com merge por squash quando libera; cada salvamento num commit da `createCommitOnBranch`, seguido do merge da `main` quando o PR está atrás dela; e nenhuma gravação direta na `main`.
- Botões que encolhem sob o dedo e voltam numa mola (nada disso com "reduzir movimento"), e animações em loop que pausam fora da tela.
- Jogo em `/play`: o hangar com as seis naves e a escolha guardada; o voo pelo teclado (empuxo, giro, turbo e pouso na primeira plataforma, sem sair da plataforma) e pelo joystick no celular; a seção que abre ao pousar, com o link para o site, fechando por Escape e pelo botão, sem abrir de novo até a nave sair, e sem o teclado pilotar enquanto ela está aberta; as páginas em português e espanhol e `/en/play` levando a `/play`; o aviso sem WebGL; e a política de segurança do site, sem violações. O Chromium dos testes desenha o WebGL por software, e no CI cada comando à página pode levar um segundo: por isso os testes de pouso esperam o relógio do voo andar (`data-time`), dão um impulso cronometrado de dois segundos e meio, que acaba bem antes da primeira plataforma, e deixam a plataforma segurar a nave, em vez de reagir ao que leem da página: ela segura a nave mesmo que o impulso acabe um segundo antes ou um segundo depois. As capturas visuais não incluem o jogo, porque cada quadro sai diferente.
- Tema que segue o sistema, troca pelo botão com o círculo (ou na hora, com "reduzir movimento"; ou aos poucos, sem mexer nas páginas, com o menu aberto), fica guardado para a próxima visita e já vale antes do primeiro desenho da página, inclusive na página de erro do layout.
- Aparência idêntica às imagens de `tests/snapshots/`, em desktop e em celular. As vistas principais têm imagens nos dois temas, as do tema claro com o prefixo `light-`, e o topo, o menu, as experiências e o contato têm imagens em português e em espanhol, com os prefixos `pt-` e `es-`. O Playwright usa o tema escuro por padrão (`colorScheme: 'dark'` no `playwright.config.ts`), e os testes do tema claro pedem o outro com `test.use({ colorScheme: 'light' })`.

Os testes procuram textos visíveis, como títulos de seções e cargos. Se mudar esses textos a pedido, atualize os testes na mesma mudança. Nunca enfraqueça ou remova um teste para fazê-lo passar.

Os testes visuais só rodam no Linux, dentro do contêiner `mcr.microsoft.com/playwright:<versão>-noble` usado pelo CI, porque cada sistema desenha fontes de um jeito. No macOS e no Windows, `pnpm test:e2e` os ignora. Quando o CI falhar num teste visual, baixe os artefatos `test-results-1` e `test-results-2` da execução com `gh run download` (cada job `e2e` publica o seu, se falhar) e examine as imagens `*-actual.png` e `*-diff.png`. Se a mudança não foi pedida, corrija o código. Se foi, copie cada `*-actual.png` para `tests/snapshots/<desktop|mobile>/`, com o nome sem o sufixo.

O Playwright grava a imagem de um teste visual novo e aprova o teste. Por isso cada job `e2e` compara `tests/snapshots/` antes e depois dos testes e falha no passo **Fail on new screenshots** até que a imagem seja versionada. A imagem nova vem no artefato do mesmo job, em `tests/snapshots/`; revise-a antes de versionar. Os testes visuais rolam até cada seção e esperam a entrada do cabeçalho terminar antes da captura. Máscaras e seletores ficam limitados à seção, como em `#experience ...`, porque todas estão na mesma página.

Capturas que variam entre execuções aparecem como teste instável no CI. As causas já encontradas, e o que evita cada uma:

- Clicar num elemento enquanto o bloco dele ainda entra na tela (`Reveal`) às vezes faz o Playwright rolar a página antes do clique. Antes de clicar, espere a entrada terminar, com `toHaveCSS('opacity', '1')` no bloco.
- Depois de um clique que abre ou fecha algo, espere as transições (`waitForTransitions`) antes de centralizar o elemento para a captura.
- Imagens reduzidas por um `transform: scale()` sob um `filter` saíam um pouco diferentes de um quadro para outro. Os aparelhos dos projetos usam `zoom`, que desenha a imagem no tamanho final, e a captura do carrossel usa "reduzir movimento", para as setas pularem direto ao cartão, sem deslizar.

Uma seção que muda de altura desloca as de baixo por frações de pixel, e o texto delas sai com outro antisserrilhado, o que reprova as imagens mesmo sem nenhuma mudança nelas. Antes de regravar, confira que a diferença é só essa: as imagens antiga e nova coincidem com um deslocamento de no máximo um pixel na vertical.

## Git, pull requests e publicação

- `main` é a única branch permanente e a branch de produção do site `brgarcias-portfolio` no Netlify. Cada merge em `main` publica o site em <https://brgarcias-portfolio.netlify.app>. Não crie `develop` nem outra branch permanente.
- Crie uma branch de trabalho a partir de `main` atualizada, com prefixo como `feat/`, `fix/`, `docs/`, `test/` ou `chore/`.
- Mensagens de commit seguem Conventional Commits, em inglês, como `fix: keep the menu usable after a fast close`.
- Os commits precisam de assinatura verificada pelo GitHub. O hook de pre-commit roda o Prettier nos arquivos preparados. Nunca use `--no-verify` nem desative a assinatura.
- Abra o PR com destino a `main`. O título segue Conventional Commits, e título e descrição ficam em português.
- O Netlify gera um Deploy Preview para cada PR, em `https://deploy-preview-<número>--brgarcias-portfolio.netlify.app`. A `main` exige quatro checks do Netlify: `Header rules - brgarcias-portfolio`, `Pages changed - brgarcias-portfolio`, `Redirect rules - brgarcias-portfolio` e `netlify/brgarcias-portfolio/deploy-preview`.
- O job `quality` do GitHub Actions também roda em cada PR. Só faça o merge com ele aprovado.
- A `main` exige histórico linear e PR atualizado em relação a ela. Faça merge só com **Squash and merge**, depois que os checks passarem.
- Nunca faça push direto ou force push em `main` e nunca altere as proteções da branch.
- Os PRs que o painel de conteúdo abre, em branches `cms/...`, são do Bruno: ele publica pelo painel. Não faça merge, não feche e não mude esses PRs, a não ser que ele peça.
- Não publique pelo Netlify CLI. A produção só muda por merge em `main`.
- A configuração do Netlify fica no painel do site. Não há `netlify.toml` no repositório.
